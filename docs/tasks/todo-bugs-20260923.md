# Pre-1.0 bugs and gaps, 2026-09-23

Status: **open items**, from the pre-1.0 review on 2026-09-23. That review
combined hands-on testing of the release binary with two simulated first-time
users (Sonnet and Haiku) who learned Petal from the docs alone. Everything here
was reproduced at `d995057`. The full write-up is in
`.temp/sim-user-testing.md`, which is not checked in.

Fixed in the same session, so not listed below:

- The README claimed "back-propagation is built in", but Petal has forward-mode
  AD only. The claim is now worded accurately.
- `petal check` exited 0 on an undefined name, a bad arity or a bad named
  argument. These are now errors, and `check` exits 1 on them without
  `--strict`. `--lenient` restores the old exit code for corpus sweeps.
- `Getting_Started.md` led with building from source. It now leads with the
  installer.
- Runaway recursion ate memory until the OS killed the process (see §2).

Fixed since, and removed from the list: Garden failing to build against the
fx-hashed `alloc_map` (`7ebc53f`), the per-frame call-path copy (§1.2), and
the missing formatter (`petal fmt`).

Ranked: release blockers first, then silent wrong results, then friction.

## 1. Release blockers

### 1.1 The installer 404s

`https://petal-lang.org/install.sh` and `uninstall.sh` return 404. The
`petal-lang.org` repo has `frontend/public/install.sh`, but it isn't deployed.
`github.com/andyfischer/petal/releases/latest/download/petal-aarch64-apple-darwin.tar.gz`
also returns 404, so there's no published release, or the repo is private.
The first command in the README and in Getting Started fails. Cut a release
with `release-petal.yml`, deploy the site, and test the one-liner on a clean
machine. See [dev/releasing.md](../dev/releasing.md).

### 1.2 Memoization makes recursion slow and memory-hungry

**Fixed.** `petal run` no longer memoizes unless a policy is named (`fib(27)`:
4.6 MB, 0.04 s; `fib(30)`: 4.7 MB, 0.18 s). With memoization on, scopes stop
at 96 frames deep, so linear recursion is linear (7.9 MB at depth 4,900), and
the table is bounded at 96 MB of records (`fib(27)`: 131 MB, 0.25 s). The
numbers and what is left (`state` in a deep recursion, path interning) are in
[dev/performance.md](../dev/performance.md) and
[dev/memo-scopes.md](../dev/memo-scopes.md) "Bounds". What follows is the
report as filed.

Under the default `fast` policy, memory grows with every nested call
(re-measured 2026-10-08 at `47d1e0e`):

| Program | `fast` | `--policy baseline` |
|---|---|---|
| `fib(27)` (naive, ~630k calls) | 541 MB, 0.47 s | 4.5 MB, 0.04 s |
| linear recursion, depth 1,000 | 30 MB | |
| linear recursion, depth 2,000 | 100 MB | |
| linear recursion, depth 4,900 | 479 MB | 7 MB |

Flat loops of calls are fine: 1M calls to `g(x)` use 4 MB. So the cost is in
nested frames, and it is still quadratic in depth under `fast`.

Frames no longer copy their caller's call path (`VmFrame::path` holds only the
frame's own parts, and `Vm::full_path_into` builds the whole path on demand),
which is why `baseline` at depth 4,900 fell from 245 MB to 7 MB. What is left
is the **memo records**, which still pay for a full path per nested call.
Someone will benchmark `fib` in the first hour after launch. Options:

- Bound the memo table, or skip memoizing for `petal run` of a console
  program, where there is no next frame to replay into.
- Have memo records share path prefixes the way frames now do. See
  [dev/state-call-paths.md](../dev/state-call-paths.md) for what a path must
  keep meaning.
- Add `fib(30)` and a depth-10k recursion to the perf suite, with a memory
  ceiling.

Repro: `printf 'fn fib(n) if n < 2 then n else fib(n-1) + fib(n-2) end end\nprint(fib(27))\n' > f.ptl; /usr/bin/time -l petal run f.ptl`

### 1.3 The `state` example doesn't do what it says under `petal run`

[writing-petal-guide.md](../writing-petal-guide.md) §3 and
[language-guide.md](../language-guide.md) §State both show (the README no
longer does):

```petal
state hits = 0
hits += 1
print(hits)    // 1 on the first run, 2 on the second, ...
```

Separate `petal run` invocations print `1` every time, because nothing is
persisted between processes. A "run" means a re-execution inside a
long-lived host: a frame, or a hot reload. The Sonnet user hit this unprompted
and called it the most misleading thing in the onboarding docs. It's the
headline feature. Fix the example so it shows state working within one run
(call `counter()` several times, or loop), and say plainly what "run" means.

### 1.4 The version and status line don't say 1.0

`petal --version` prints `0.1.0`, which comes from `core/Cargo.toml`. The
README says "This project is in an early, experimental phase. Language
stability is not guaranteed." There's no CHANGELOG.

## 2. Runaway recursion: fixed, with follow-ups

`fn f(n) f(n+1) end` used to grow for about 45 s, to about 2 GB, and then get
SIGKILLed with exit 137 and no output. Recursing through a callback
(`fn f(n) map([n], fn(x) -> f(x + 1)) end`) aborted at once with a Rust
`stack overflow`. Both now stop with `Error: Stack overflow …` and a stack
trace, in which runs of repeated frames are collapsed and long traces are
elided. The limits are in `core/src/backend/bytecode/vm/mod.rs`:

- `MAX_CALL_DEPTH` = 20,000 frames (raised from 5,000 once §1.2 was fixed).
  A runaway now fails in a few milliseconds at about 15 MB peak.
- `MAX_STATE_CALL_DEPTH` = 5,000 frames for path-keyed `state`, whose keys
  are quadratic in depth. A runaway that declares `state` fails in 0.9 s at
  about 480 MB, as every runaway did before.
- `SYNC_STACK_BUDGET` = 1 MiB of native stack (256 KiB on wasm) for callbacks
  nested inside one another. That's about 340 levels in a release build and
  only about 40 in a debug build, because debug step-loop frames are about
  25 KB each against about 3 KB in release.
  `test/vitest/stack-overflow.test.ts` covers both.

Follow-ups:

- `MAX_CALL_DEPTH` could go to 100,000 as far as calls go (58 MB, 20 ms in
  both build profiles). What holds it at 20,000 is the value a recursion can
  return: `str`, `==` and the collector recurse on the native stack over a
  nested value, and overflow it between 20,000 and 30,000 levels in a release
  build on an 8 MB thread. A debug build already overflows in `str` at 3,000
  levels, and a loop can build a value that deep under any call limit
  (`var l = nil; for i in range(0, 40000) do set l = {next: l} end;
  print(str(l))` aborts). Make those walks iterative, then raise the limit.
- Shrink the native stack per callback level, so debug builds allow more than
  40. Alternatively, run callbacks without nesting a step loop by resuming the
  intrinsic from the main loop.
- Neither limit can be configured. An embedder that runs Petal on a small
  thread stack may want to lower `SYNC_STACK_BUDGET`.

## 3. Silent wrong results

### 3.1 A leading `-` on a continuation line starts a new statement

[writing-petal-guide.md](../writing-petal-guide.md) §8 documents this: a
weighted sum written down the page with a leading `-` returns only the last
line, and it passes `check --strict`. It's a silent wrong answer, and HN will
quote it. Add a lint: an expression statement that starts with a unary `-`,
directly after an expression statement whose value is discarded, is almost
certainly a broken continuation.

### 3.2 Enum variants are global names, and collisions are silent

```petal
enum A
  None,
end
enum B
  None,
end
print(None)        // no warning; which None?
```

`let Red = 5` followed by `enum Color Red end` makes `print(Red)` print `Red`.
The `let` is overridden silently. Report a variant name declared twice, and a
variant that shadows a binding.

### 3.3 Enum names aren't accepted as type annotations

`fn f() -> Shape` warns `unknown type name Shape`. The Sonnet user hit this on
the first try, modelling a result type as an enum. Either accept enum names in
the type vocabulary (as class names are), or say in
[writing-petal-guide.md](../writing-petal-guide.md) §8 that they aren't.

## 4. Performance

### 4.1 `++` in a loop is O(n²)

`out = out ++ "x"` takes 0.22 s at 20k iterations, 0.9 s at 40k and 5.9 s at
100k, the same under both policies. The usage guide §5 recommends exactly this
loop as the string-repeat workaround. Add `repeat(s, n)`, and either make
append-to-a-uniquely-owned-string amortized O(1) or point people at `join`.

## 5. Missing basics people will ask about

- **No I/O.** There's no `read_file`, `read_line`, argv, env, clock or
  `exit(code)`. Every one of these is `Unknown builtin`. That's defensible for an
  embedded language, but the README pitches a standalone CLI. Either state the
  positioning in the README ("the host provides I/O; the CLI is for learning
  and tooling"), or add a minimal `std.io`.
- **No recoverable errors.** There's no `try` or Result convention, and the
  docs never say how a program should report or handle an error. The Sonnet
  user improvised an `enum` + `match`. At least document the idiom.
- **Records are the only dictionary, with string keys only.** `m[5] = v` gives
  `Cannot index-assign record with int`. Neither guide says "use a record as a
  dictionary" or shows `r[k] = v`. The Haiku user wrote an O(n²) list-of-pairs
  word counter because of this.
- There's no REPL, test runner or VS Code extension.

## 6. Tooling friction

- **A mistyped subcommand becomes a file error.** `petal repl` and
  `petal test` print `Error reading file 'repl': No such file or directory`.
  When the argument has no `.ptl` extension and doesn't exist, say
  "unknown command" and suggest a real one.
- **The LSP doesn't run the unknown-name pass.** `print(b)` with `b` undefined
  gets no diagnostic in the editor, though `check` reports it. The LSP doesn't
  know the host, so it needs a host setting (initialization option or a
  project file) before it can run the pass without false errors on Garden
  scripts.
- **LSP hover has no types.** Hovering `let a = 1` shows `(variable) a`.
- **An unclosed block doesn't name its opener.**
  `Expected \`end\`, got end of input [line 3, column 1]` should point at the
  `fn` on line 1 that was never closed.
- **A cross-module stack trace drops the file name.**
  `in boom() [line 2, column 7]` doesn't say which file the call site is in.
- `let x =` followed by a line break gives `Unexpected token: a line break`,
  with no hint to keep the value on the same line or wrap it in `(`.
- **`petal run` has no `ui`, but `check` defaults to `--host ui`.** A
  newcomer's `check` passes on a script that `run` rejects with
  `Undefined variable: ui`. Say so in [CLI.md](../CLI.md), or make `check`
  default to the host `run` actually is.
- **Doc snippets are only checked with `--lenient`.** `doc-snippets.test.ts`
  now passes `--lenient`, because snippets are fragments that name things
  defined elsewhere. About 40 of them reference undefined names. It's worth a
  pass to see which are fragments and which are typos.

## 7. Docs

- [writing-petal-guide.md](../writing-petal-guide.md) §8: "Method syntax
  reaches builtins, not your own functions" made the Haiku user think class
  methods don't work with `.`. Reword it: `x.f()` finds declared methods
  (`fn Class.f`) and builtins, but not free functions.
- Document truthiness somewhere a newcomer will find it: `0` is falsy, while
  `""` and `[]` are truthy.
- Document that float division by zero is an error, not `inf`.
- Both simulated users used `var`/`get`/`set` where a plain `let` rebind
  works. Put a "you almost never need `var`" callout before the `var` table in
  §3, not after it.
