# `ui` reference

*Generated from the `@doc` and `@module_doc` in the sources (`npm run reference`); edit those, not this page.*

The petal-ui interface: drawing, input and the widget prelude.

Everything a script gets from `import ui`: the input natives, the draw
calls, layers and hit testing, text, layout, colour, the theme, the
interaction state (focus, lists, text editing, popovers, drag and drop) and
the drawn widgets. A script calls these bare, as `ui.button`, or after
`import ui: button`. A host registers the natives (`petal_ui::register_all`);
`petal lint` resolves `import ui` with no host present.

Conventions:

- **Immediate mode.** The whole script runs every frame. A widget is a
  function call that draws and returns what happened: `if button(r, "Save")
  then save() end`.
- **A rect** is `rect(x, y, w, h)`, or any `{x, y, w, h}` record. `rect`
  gives the methods (`r.right()`, `r.center_x()`, `r.inset(4)`).
- **A colour** is a `{r, g, b}` record, which is what a hex literal is
  (`:3c8cff`). `draw_rect`, `draw_polyline`, `draw_rects` and
  `draw_image`'s `tint` also take a packed int, `r * 65536 + g * 256 + b`.
- **Alpha** is a trailing `a`, 0–255, on every draw call. Strokes also take
  a trailing `width`.
- **`style`** is an optional last argument on every widget: a record that
  overrides what the theme says. `{}` is the themed widget, and leaving it
  off is the same.
- **Widget state** that outlives a frame (`list_state()`, `modal_state()`…)
  is a record you keep in `state` and pass in; the widget returns the next
  one.
- Button 0 is the left mouse button. Key names are lower case: `"space"`,
  `"escape"`, `"a"` (see `key_down`).

Modules: `ui` re-exports `ui/input` (the input, timing and frame natives),
`ui/draw` (drawing, clipping, gradients, shadows, canvases, fonts, colour
and the theme), `ui/hit` (layers, `interact`, named targets, measuring, flow
layout and retained drawing), `ui/text`, `ui/layout`, `ui/interaction` and
`ui/widgets`. The drawn widgets in `ui/widgets` are deprecated: bloom owns
them now. `ui/drag`, declarative dragging, is not re-exported: a script that
drags writes `import ui/drag`.

Guides beside this reference, in core-stdlib/ui/docs: widgets.md (the
reasoning behind a widget, worked examples and the theme tokens), drawing.md
(the draw primitives in depth), drag.md (declarative dragging) and
host-contract.md (what a host has to do to draw any of this). Two apps to read:
`garden/examples/panels/gallery.ptl` uses every widget, and
`examples/ui/layers` is a HUD over a "world" (layers, `pointer_captured`, a
modal, `cached_layer` with `draw_rects`, flow layout and `ui_measure`). To
test a UI with no window, `petal_ui_headless::harness::Headless` runs a
script headless, and `petal-ui-run` does the same from the command line.

**See also:** [`ui/input`](#uiinput), [`ui/hit`](#uihit), [`ui/draw`](#uidraw), [`ui/text`](#uitext), [`ui/layout`](#uilayout), [`ui/interaction`](#uiinteraction), [`ui/widgets`](#uiwidgets), [`ui/drag`](#uidrag)

## `ui/input`

The input half of the petal-ui interface: the pointer, the keyboard, timing
and the frame.

Input is polled, never called back. An *edge* (`mouse_pressed`,
`key_released`, …) is true on one frame. The `ui` module re-exports every
name here, so a script that writes `import ui` has them all. A host that
registers only this half (a console with its own video, say) has its
scripts write `import ui/input`, and loading them needs none of the draw
natives.

### The keyboard

Key names are lower case and name the key, not what it types; `key_down`
lists them. For an app's commands, `shortcut` (`ui/interaction`) is usually
better than `key_pressed`: it stays quiet while a text field has the
keyboard.

#### `key_down`

```petal
key_down(key: string) -> bool
```

Whether `key` is held.

A key is named for the key, not for what it types: `"a"`–`"z"`,
`"0"`–`"9"`, `"space"`, `"return"`, `"escape"`, `"tab"`, `"backspace"`,
`"up"`/`"down"`/`"left"`/`"right"`, `"pageup"`, `"pagedown"`, `"home"`,
`"end"`, `"delete"`, `"insert"`, `"shift"`, `"ctrl"`, `"alt"`, `"cmd"`,
`"f1"`–`"f12"`, `"minus"`, `"equals"`, `"comma"`, `"period"`, `"slash"`,
`"backslash"`, `"semicolon"`, `"quote"`, `"backquote"`, `"leftbracket"`,
`"rightbracket"` (the list is `petal::keys::KEY_NAMES`). Enter is
`"return"`; `+` is `"equals"` with `mod_shift()`. Any other name is never
down, so `petal lint` warns about one written as a literal and names the
likely key (`key_pressed("enter")`: did you mean `"return"`?). The keypad
has no names of its own: keypad Enter is `"return"`, and its digits and
`-` `.` `/` `=` are the main-row keys.

**Parameters**

- `key` (`string`): A key name, lower case (above).

**See also:** [`key_pressed`](#key_pressed), [`key_released`](#key_released), [`ui.shortcut`](#shortcut)

## `ui/hit`

Layers and hit testing, named targets, measuring, flow layout and retained
drawing. `ui` re-exports every name here.

Immediate mode has no z order: a button drawn early cannot know a panel
drawn later covers it. A layer is how a script says so (`ui_layer`,
`with_layer`). The raw tests, `hovered` and `clicked`, look at the pointer
and the rect and nothing else; the layered ones (`interact`, `ui_hot`,
`ui_block`) are what widgets use, and they know about what is drawn on top,
about modal dialogs and about clipping. Every registered rect can carry an
id, which a script, a test or an agent can look up (`ui_target_rect`)
instead of re-deriving a layout.

**See also:** `ui`, [`interact`](#interact), [`ui_layer`](#ui_layer)

### Layers and hit testing

The layers the built-in widgets use are 0, 1000, 2000 and 3000
(`UI_LAYER_BASE`, `UI_LAYER_POPUP`, `UI_LAYER_MODAL`, `UI_LAYER_TOOLTIP`);
an app's panels go in between. `interact` says how the pointer's one owner
is chosen, the one-frame gap, and why a click belongs to what was pressed.

#### `ui_layer`

```petal
ui_layer()
ui_layer(n: int)
```

The current layer; with `n`, put everything from here on on layer `n`. A
frame starts on layer 0.

A layer orders two things. **Drawing**: the host draws lower layers first,
and within a layer in the order drawn, so a tooltip drawn in the middle of a
frame on a high layer still comes out on top. **The pointer**: it has one
owner, the rect in front under it, on the highest layer with a registered
rect there (unless a higher layer is modal). See `interact`.

**Parameters**

- `n` (`int`): The layer to switch to; higher is in front.

**Returns** The current layer, or with `n` the layer it replaced.

**See also:** [`with_layer`](#with_layer), [`ui_overlay`](#ui_overlay), [`ui_modal`](#ui_modal), [`UI_LAYER_POPUP`](#ui_layer_popup)

*Source: [`core-stdlib/ui/src/_frame.ptl:238`](../src/_frame.ptl#L238) (re-exported from `ui/_frame`)*

#### `interact`

```petal
interact(r, id = nil, wants = nil)
```

The pointer and one rect, layered: registers `r` on the current layer and
says what the pointer did to it. Every widget is built on it.

| Field | True when |
|---|---|
| `hover` | The pointer is over the rect and nothing above has the pointer. |
| `down` | The left button is held and went down inside the rect. Stays true if the pointer slides off. |
| `pressed` | The left button went down this frame, over the rect. |
| `released` | The left button came up this frame, over the rect. |
| `click` | Released over the rect, having been pressed inside it while it was there. |

Of overlapping rects only the one in front has the pointer: the highest
layer, then the rect registered last on it (drawn on top). So a button drawn
over a list row takes its click alone, and the row takes clicks on the rest
of it. Only the owner is hot, is `down` for a press, and gets the `click`. A
rect that was not registered last frame (new, or moved) is answered by the
pointer and the layers alone until it is. The clip in force counts too: a
row scrolled half out of its list is not hot over the clipped part.

What is above a rect is answered from the rects registered *last frame* and
the rects already found hot *this frame*. A covered widget is inert from the
frame after its cover appears (and from the same frame if the cover's code
runs first). The one gap: a widget on a lower layer that runs *before* a
higher one that first appears this frame sees one frame of `hover`, and a
`pressed` if the press lands on exactly that frame. `click` has no gap,
because by the release the cover is a frame old, so use `click` for
anything that must not fire through a panel.

A click belongs to what was pressed: on the release, only rects that were
registered under the press point when the button went down (last frame's,
plus anything the press frame itself registered) get `click` (matched by
layer and rect, or by `id`, so a button whose rect moves while held keeps
its click if it has an id). A row of a panel the click itself opened, or a
widget that *appears* between the press and the release, gets `released`
but not `click`. `down` still follows the press point alone.

**Parameters**

- `r`: The rect.

### Flow layout

#### `flow_begin`

```petal

```

Start a flow in `r`: a cursor that hands out rects one after another, so a
panel is written without `y = y + 17` at every line. Flows nest: a row of
buttons is a horizontal flow begun on a rect a vertical one handed out.
Nothing here draws or clips, and a flow is not stopped at the end of its
region: the rects go on past it, and `flow_end()` says how far they went,
which for a region inside a scroll view is the content height.

**Options**

| Key | Meaning |
|---|---|
| `pad` | Insets the region on every side. |
| `gap` | Left between consecutive rects. |
| `axis` | `"y"` (the default) runs downward; `"x"` runs across. |

**Example**

```petal
flow_begin(panel, {pad: 8, gap: 4})
draw_text("Settings", flow_next(20), title)

if button(flow_next(80), "Apply") then apply() end
if button(flow_next(80), "Cancel") then close() end

```

### Retained drawing

A frame's commands live one frame. For something that changes rarely and
costs a lot to say, say it once: `cached_layer` keeps what its body drew,
and `draw_rects` (`ui/draw`) is one command for many rects.

#### `cached_layer`

```petal
cached_layer(key, r, body)
```

Retained drawing: run `body()` only when `key` or the rect's size changes
(or the host has lost what it kept); on every other frame the host redraws
what the body drew last time, at the rect's current position. For something
that changes rarely and costs a lot to say: a minimap of several hundred
rects, a title poster.

- The body draws in the layer's own coordinates, and the result is clipped
  to the rect's size. Moving the rect does not run the body.
- The body only draws. It does not run on most frames, so an `interact` or a
  `state` inside it would come and go.
- Layers nest. The body must not open an offscreen `layer` or use `clip`
  (the replace form); `clip_push` is fine.
- Each call site is one layer, and in a loop one per iteration, like `state`.
- A layer that is not drawn for a frame is let go, and recorded again when it
  comes back.

**Parameters**

- `key`: Any value, compared by content: a version counter, a record of the inputs.
- `r`: Where to draw it; only its size reruns the body.
- `body`: A function of no arguments that draws.

**Example**

```petal
# A minimap of a few hundred cells, emitted once per map version.
cached_layer(map_version, minimap_rect, fn()
  draw_rects(cells, PALETTE)          # (0, 0) is the layer's top-left
)
```

**See also:** [`draw_rects`](#draw_rects)

### Drawing and measuring text

A text style is a record (see `draw_text` for its fields). Measure with the
record you draw with. `ui/text` has the helpers built on these: alignment,
truncation, wrapping, text on a path and carets.

#### `draw_text`

```petal
draw_text(text, x, y, size, r, g, b, a = 255)
draw_text(text, x, y, size, c, a = 255)
draw_text(text, pos, size, c, a = 255)
draw_text(text, pos, style)
draw_text(text, x, y, style)
```

Draw a run of text. `y` (or `pos.y`) is the top of the line. With a style
record, omitted fields mean plain text (the host's own face, upright,
regular), so a style is a diff against the plain call. Measure with the same
record (`text_width(s, style)`) and the two agree.

A **text style** is a record; every field is optional.

| Field | Meaning |
|---|---|
| `size` | Pixel size. |
| `color` | A colour record; its `a` is the run's alpha. |
| `font` | A face: an installed family name (`"Georgia"`, any case), a host role (`"ui"`, `"mono"`), or a fallback list (`"Georgia, ui"`). A family the host can't find draws, and measures, in the default face. |
| `weight` | 400 regular, 600 semibold, 700 bold. |
| `italic` | `true` for italic. |
| `spacing` or `tracking` | Extra pixels between letters. Measured as well as drawn. |
| `shadow` | `true`, or `{dx, dy, color, a}`: one copy under the text, offset (1, 1) and black at alpha 160 by default. |
| `outline` | `true`, a colour, or `{color, width, a}`: a ring around the glyphs, 1 px and black by default. |

`shadow` and `outline` fade with the text's own alpha. See docs/usage/text-and-fonts.md
for which hosts look font families up.

**Parameters**

- `pos`: Where the run starts: `{x, y}`, `y` the top of the line.
- `style`: A text style record (above).
- `size`: A pixel size, in the host's default face.
- `c`: The colour, with `size`.

**Example**

```petal
let title = {size: 22, color: :ffffff, tracking: 2, outline: :000000}
draw_text("ROUND 3", 40, 20, title)
draw_text("#482", {x: 60, y: 20}, {size: 15, color: :d8dee9, weight: 700})
```

**See also:** [`text_width`](#text_width), [`font`](#font), [`ui.draw_text_center`](#draw_text_center), [`ui.draw_text_right`](#draw_text_right)

#### `theme`

| Token | Role |
|---|---|
| `bg` | Window / canvas floor. |

### Focus and shortcuts

At most one widget id has the keyboard, and the runtime decides who once
per frame, before the script runs. A press on a rect that declared
`{text: true}` or `{focus: true}` (see `interact`; every text field does)
gives it the keyboard on that same frame. A press anywhere else takes it
away, unless it lands on a higher layer than the focused widget, as a menu
opened from a field does. While a widget has the keyboard, the keys it
claims are not the app's shortcuts: a text widget claims every key pressed
without Cmd/Ctrl and the editing chords (Cmd+A, C, X, V, Z, Shift+Z, Y, and
Cmd with an arrow, Backspace or Delete), and any widget claims the chords it
listed in `keys`. So `shortcut("v")` and `shortcut("escape")` are quiet
while the user types, and `shortcut("cmd+s")` still fires. The fields read
this focus, so an app keeps no focus record of its own. An id is a string
or an int.

#### `has_focus`

```petal
has_focus(id)
```

Whether `id` has the keyboard this frame (including a `focus_request` made
earlier in this run).

**Example**

```petal

```

### Text editing

The logic of `text_field` and `text_area` with no pixels of their own, for
a field with its own chrome. A press inside a field focuses it. A press
anywhere else takes the keyboard away, unless something on a higher layer
took the press (a popup opened from the field), so a click on the rest of
the UI ends the edit without wiring up Escape.

#### `text_field_update`

```petal
text_field_update(id, r, buf)
text_field_update(id, r, buf, style)
```

The logic of a single-line text field with no pixels of its own: focus,
caret, selection, clipboard, undo and Return. An app with its own look keeps
the editing logic, the fiddly part, and draws the box itself; bloom's
`draw_text_field(r, res, focused, opts)` is the stock look. `buf` is a plain
string kept in the caller's `state`; the caret, the selection and the undo
history are kept per call site.

| Input | Does |
|---|---|
| click / shift+click / drag | focus and place the caret / extend the selection / select |
| a press anywhere else | gives the focus up, unless a higher layer took the press |
| double click / triple click | select the word / everything |
| left, right, home, end | move the caret; with shift, extend the selection |
| alt or ctrl + left/right | by word; cmd + left/right goes to either end |
| backspace, delete | the selection, else one character (alt/ctrl+backspace: back to the word start; cmd+backspace: to the start) |
| cmd+A | select all |
| cmd+C / cmd+X / cmd+V | copy, cut, paste through the clipboard |
| cmd+Z, cmd+shift+Z or cmd+Y | undo, redo |
| return | sets `submitted` |
| escape | sets `cancelled` (the field keeps the focus; a caller that reverts drops it) |

Cmd and Ctrl are interchangeable. Typing replaces the selection; a run of
typing is one undo step, a word at a time. A paste loses its line breaks.
When `buf` is not what the field last returned (the app cleared or replaced
it), the history is dropped.

**Parameters**

- `id`: The focus id: a string or an int.

**Options**

| Key | Meaning |
|---|---|
| `size` | Text size; must match what the draw half uses, or click-to-place lands off. |
| `font` | The face; must match the draw half too. |
| `text_style` | A whole text style record, for an app with its own type ramp, in place of `size` and `font`. |
| `inset` | Padding between the box and the text. |
| `pointer` | `false` keeps the mouse out for this frame (the field is under a modal). |
| `scroll` | `true` turns on horizontal scrolling: the result's `scroll` is how far the text is shifted left to keep the caret in the box, and the draw half shifts by it too. |

**Returns** `{text, caret, submitted, changed, anchor, sel_start, sel_end, scroll, overflow, blurred, cancelled}`. `caret`, `anchor`, `sel_start` and `sel_end` are character offsets; `sel_start == sel_end` means no selection. `blurred` is true on the frame after the field lost the keyboard, the cue to apply an edit on blur.

**Example**

```petal
let res = text_field_update("name", r, buf, {text_style: MY_STYLE, inset: 0})
buf = res.text
for q in text_range_rects(buf, MY_STYLE, res.sel_start, res.sel_end) do
  draw_rect(r.x + q.x, r.y + q.y, q.w, q.h, MY_HIGHLIGHT)
draw_text(buf, {x: r.x, y: r.y}, MY_STYLE)
```

**See also:** [`text_area_update`](#text_area_update), [`ui.text_field`](#text_field), [`ui.clipboard_get`](#clipboard_get)

*Source: [`core-stdlib/ui/src/interaction.ptl:534`](../src/interaction.ptl#L534)*

#### `text_area_update`

```petal
text_area_update(id, r, buf)
text_area_update(id, r, buf, style)
```

`text_field_update` for text with line breaks (captions, notes, a chat
message), with no pixels of its own. The text wraps to the box
(`text_wrap_rows`); Return inserts a line break, so there is no
`submitted`; a paste keeps its line breaks (a CR of a CRLF is dropped).
Everything else is the field's: focus, selection, the clipboard and undo.

| Input | Does |
|---|---|
| return | inserts a line break |
| up / down | a row up or down, keeping the column across short rows |
| cmd + up / down | to the start / end of the text |
| home / end, cmd + left / right | to the start / end of the row |
| wheel over the box | scrolls text taller than the box (by rows) |

quiet frame the wheel is free to scroll away from it.

**Options**

| Key | Meaning |
|---|---|
| `size` | Text size; must match the draw half. |
| `font` | The face; must match the draw half. |
| `text_style` | A whole text style record, in place of `size` and `font`. |
| `inset` | Padding between the box and the text. |
| `line_gap` | Pixels added to the face's line height between rows (2). |
| `pointer` | `false` keeps the mouse out for this frame. |
| `select_all` | Select the whole text on this frame (text the next keystroke should replace). |

**Returns** `{text, caret, changed, anchor, sel_start, sel_end, scroll, overflow, rows, line_h, content_h}`: `rows` is the wrap (`text_wrap_rows` rows), `scroll` how many pixels the text is shifted up, `content_h` its whole height.

**Example**


### Popovers and menus

At most one menu or popover is open: opening one closes the others. The
runtime closes the open one before the frame runs, on Escape or a press
outside it, and that press reaches nothing underneath. So the press that
opened a menu can't close it, and a menu shown every frame still works.
While one is open, `shortcut(chord)` is quiet, and an Escape that closed it
is not also the app's. `shortcut(chord, id)` answers for the open popover.
Widgets need no guard of their own while it is open. Code that reads the
mouse itself (`mouse_pressed` and `point_in`) still stands down while
`menu.open`.

#### `popover_open`

```petal
popover_open(id)
```

Open popover `id` from the next frame. The runtime holds which popover is
open, by id, so there is no record to thread. At most one is open: opening
one closes the rest. Escape and a press outside close it before the frame
runs, and that press reaches nothing underneath. While it is open it has the
keys: `shortcut(chord)` is quiet and `shortcut(chord, id)` answers.

## `ui/widgets`

**Deprecated:** bloom owns the widgets: `import bloom` (core-stdlib/bloom/docs/components.md).

The drawn widgets: buttons, scrollbars, text fields and areas, context menus
and popovers, checkboxes, sliders, inspector fields, tab bars, tooltips,
modals, badges and cards, splitters, tables and the load view. Deprecated:
bloom (core-stdlib/bloom) owns the widgets now, and every name here has a
bloom replacement, which `petal lint` rule `ui-widget-moved` names at
each call. `ui` still re-exports these during the deprecation period. The
parts that draw nothing (focus, list state, text editing, drag and drop, the
load state) are `ui/interaction` and stay.

Every widget takes an optional trailing `style` record; any key it leaves out
comes from `ui_theme()`, and `{}` (or the shorter form) is the themed widget.
A widget returns its new value (`checkbox` the new bool, `button` true on the
frame it was clicked) rather than calling back. Buttons, checkboxes,
toggles, radios, tabs and sliders ease their hover, press and check
transitions (about 120 ms); at rest they paint the exact resting colours, so
a still frame is pixel-stable. Where it pays, a widget comes in three forms:
`x_update` (logic, no pixels), `draw_x` (pixels, no logic) and `x` (both).
Widget state is per call site, so in a loop over a list that can reorder,
key the loop (`for item in items key item.id do`) so each widget's state
stays with its item.

## `ui/drag`

Declarative dragging: the view says where each element is and which model
states a drag can reach, and the engine does the rest. It renders each
reachable state, finds the dragged element in each rendering, and builds the
interaction from those positions: snapping, floating, reordering, drop
targets, and the animation of everything that moves. `ui` does not
re-export it: a script writes `import ui` and then `import ui/drag`.

```petal
state items = ["A", "B", "C"]
fn view(items)
  for i in range(0, len(items)) key items[i] do
    let r = place(items[i], rect(40 + i * 70, 100, 60, 60))
    draggable(items[i], r, fn() closest(moves(items, i)) |> floating() end)
    place(items[i], r, fn(p) draw_rect(p, COLORS[items[i]]) end)
  end
end
let d = drag_session(items, view)
view(d.preview)
if d.dropped then items = d.drop end
```

Three calls do the work: `place(key, value)` says where `key` landed and
returns the value to draw; `draggable(key, rect, spec)` makes a press on
`rect` start a drag of `key`; `drag_session(model, view)` is the engine.

A drag spec is data: tagged records built by `fixed_state`, `closest`,
`floating`, `snap_radius`, `when_far`, `drop_target`, `on_drop`,
`switch_to`, `between` and `vary`, over candidate states from `moves`,
`moves_nested`, `tree_moves` and `choices`. The engine resolves it once, at
drag start, into a table of positions; frames during the drag only read
that table. The renderings are hypothetical calls (`speculate`): their
drawing and hit-test registrations are dropped, and every `state` write,
`set` and random draw is put back, so the view can be ordinary
immediate-mode code that calls widgets with their own state.

The guide, with worked examples and the mistakes to avoid, is
core-stdlib/ui/docs/drag.md; the design is
docs/proposals/declarative-dragging.md.

Mark where `key` landed in this rendering, and get back the value to draw.
Outside a drag that is `value` eased from where `key` was last frame, so a
keyed element that moves animates (layout animation); the dragged element
under `floating` follows the pointer. Inside a speculation it records
`value` and returns it unchanged. Keys compare like `for … key` keys and
must be unique on screen.

With `body`: then call `body(v)` with the displayed value, on the drag layer
with the clip suspended while `key` is dragged or settling after a drop, so
the dragged element is drawn on top of everything it passes over. Not run
while the engine speculates, which needs only the position.

**Parameters**

- `key`: The element's identity.
- `value`: A rect, a point, a number or a colour.
- `body`: Draws the element: `fn(v)`, given the displayed value.

**Returns** The value to draw (nil with `body`).

**Example**

```petal
let r = place(item.id, rect(x, y, 60, 60))
place(item.id, r, fn(p) draw_rect(p, item.color) end)
```

**See also:** [`draggable`](#draggable), [`drag_session`](#drag_session), [`place_origin`](#place_origin), [`PLACE_RATE`](#place_rate)


#### `between`

```petal
between(options)
```

Spec: interpolate between the options' renderings. The dragged element
moves continuously inside the region its positions in the options span
(along the segment for 2 options, over a Delaunay triangulation of the
positions for 3 or more) and stops at its edge. Every key that all the
options place is drawn at the blend of its values (rects, points, numbers,
colours). The preview and the drop are the option with the largest weight.
No speculation per frame.

**Parameters**

- `options`: Model states (or `fixed_state`s).

**Returns** A spec.

**See also:** [`vary`](#vary), [`closest`](#closest)

*Source: [`core-stdlib/ui/src/drag.ptl:419`](../src/drag.ptl#L419)*

#### `vary`

```petal
vary(st, paths, opts = {})
```

Spec: solve the numbers at `paths` in `st` so the dragged element tracks the
pointer, one step of the DM solver a frame (Gauss-Newton, warm-started from
the last frame, with a step-length backtrack). The preview and the drop are
`st` with the solved numbers in. The sensitivities are forward differences,
so each frame costs one speculative rendering per path plus one or two.

**Parameters**

- `paths`: One path (`["meetings", 2, "start"]`, or a field name) or a list of them; each must hold a number in `st`.

**Options**

| Key | Meaning |
|---|---|
| `bounds` | `[lo, hi]` for one path, or a list with one `[lo, hi]` (or nil) per path; either end may be nil. |
| `constraint` | `fn(state) -> bool`: a step to a state it refuses is shortened. |

**Returns** A spec.

**See also:** [`between`](#between)
