# Builtins Reference

*Generated from the `@doc` and `@module_doc` in the sources (`npm run reference`); edit those, not this page.*

The builtins every Petal program can call without an import.

The built-in functions of the Petal runtime: the ones in scope in every
program (this package), and the domain sets a file imports (the bundled
packages `noise`, `color`, `vec2`, `json`, `io` and `autodiff`). For
language syntax (variables, control flow, functions, state, pattern
matching), see the [Language Guide](language-guide.md). The drawing and
input builtins used by `petal-ui` apps (`draw_rect`, `mouse_x`, ...) are
covered in the [petal-ui README](../core-stdlib/ui/README.md); how a
browser page runs them is in [usage/embedding-web.md](usage/embedding-web.md).

`import core` binds the qualifier `core` over every builtin the package
declares, so a script can write `core.len(xs)` where a declaration or an
import of its own has taken the bare name. Nothing needs this import to
*use* a builtin: every name is in scope in every file already.

## Named arguments

**The parameter names in this reference are real.** Every builtin with a
fixed parameter list takes [named arguments](syntax/function-overloading.md#named-arguments)
under the names its signature shows, in any order after the positional ones:

```petal
print(clamp(15, lo: 0, hi: 10))                        # 10
print(map_range(value: 5, in_lo: 0, in_hi: 10, out_lo: 0, out_hi: 100))  # 50.0
print([1, 2, 3, 4].slice(start: 1, end: 3))            # [2, 3]
```

- A parameter marked `?` (`slice(collection, start, end?)`) is optional and
  may be left off, named or not. Optional parameters are always last, and one
  cannot be skipped to reach a later one: `noise(x: 1, z: 2)` is
  `noise() is missing a value for parameter 'y'`.
- A builtin listed in several forms (`random()` / `random(max)` /
  `random(min, max)`, `distance(x1, y1, x2, y2)` / `distance(v1, v2)`) takes
  the names of whichever form the call fits.
- With method syntax the receiver is the first parameter, so
  `xs.slice(start: 1)` names the ones after it.
- A name may be a keyword: `end:` is an ordinary argument label
  (`range(start: 0, end: 5)`).
- The variadic builtins — `print(args...)` and `format(template, args...)` —
  have no parameter names to give, and refuse a named argument
  (`builtin 'print' does not accept named arguments`).

A wrong name is an error when the line runs (`clamp() has no parameter named
'low'`), and from `petal lint` before that.

Each builtin's signature is written once, as a `native fn` declaration in a
package compiled into the binary (`core/packages/`): parameter names, which
are optional, the argument types the checker holds a call to, and the result
type. See [usage/ffi.md](usage/ffi.md#native-interfaces-native-fn) for the declaration
syntax. What a builtin does besides computing its result (reading the clock,
drawing, reading host data) is declared in its effect row when it is
registered; [dev/native-effects.md](dev/native-effects.md) defines the rows
and how they are checked.

## Which builtins need an import

What reads as language is **global**: it is declared by the `core` package and
in scope in every file with no import — `print`, `len`, `str`, `type`,
`range`, the casts, assertions, the collection, string and record functions,
the higher-order functions, formatting (`core/format`), the reductions and
selections of the Petal prelude (`std`), the plain math of `core/math`, and
the creative-coding math (`clamp`, `lerp`, `map_range`, `distance`, `mag`,
`smoothstep`, `random_int`, `choose`).

The **domain builtins** live in bundled packages and are in scope only in a
file that imports the package:

| Import | Names |
|---|---|
| `import noise` | `noise`, `noise_seed` |
| `import color` | `hsv`, `hsl`, `hsv_deg`, `hsl_deg`, `color_lerp` |
| `import vec2` | `vec2`, `vec3`, `normalize`, `dot`, `cross`, `limit`, `rotate` |
| `import json` | `json_stringify`, `json_parse` |
| `import io` | `symbol`, `push_output`, `binding` |

After `import noise` the names work bare (`noise(x)`), qualified
(`noise.noise_seed(1)`) and as methods (`x.noise()`); `import noise: noise_seed`
takes just the names listed. Without the import, a call is an error that says
which import to add (`petal lint` reports it, and `petal fix-imports` adds
it). Method syntax follows the same rule: `v.normalize()` reaches the `vec2`
builtin only in a file that imports `vec2` — the import of some other file of
the program does not count, and `petal lint` reports the call when the
receiver is plainly a number, string, list or vector. The values themselves need no
import: a `vec2` a function was handed still has `.x`, arithmetic and `==`.

## `core/basics`

*In scope in every program; no import.*

Output, conversion to text, type names, assertions and expectations.

**Assertions** stop the program with a message and source location when
their condition fails.

**Expectations** check something and, when it does not hold, **record** the
failure and carry on, where an assertion stops the program. They are what a
[`test` block](testing.md) checks with: every failure of a test is reported,
each with its file and line. Outside a test, `petal run` prints the recorded
failures when the run ends and exits 1. Each one returns `true` when it held
and `false` when it did not.

### `str`

```petal no-check
str(value) -> string
```

Converts any value to its string representation.

An enum variant converts to the way it is written in source:
`str(Color.red)` is `"Color.red"` and `str(Op.fight("bridge", true))` is
`"Op.fight(\"bridge\", true)"`. For the variant's bare name use `.name`
(`Color.red.name` is `"red"`).

Petal does no implicit casting. When a value has the wrong type for a slot
(a `float` where an `int` is expected, say), convert it explicitly with
`str`, `int`, `float`, `parse_int` or `parse_float`.

**Example**

```petal
str(42)        # "42"
str(true)      # "true"
str([1, 2])    # "[1, 2]"
```


### `expect_near`

```petal no-check
expect_near(actual: num, expected: num, tolerance: num, message?) -> bool
```

Records a failure when two numbers differ by more than `tolerance`, as
`expected 0.6 within 0.01, got 0.5 (off by 0.1)`. The tolerance is required
and must not be negative. A value that is not a number, and a NaN, is never
near anything.

**Returns** `true` when it held, `false` when it did not.

**Example**

```petal
expect_near(0.1 + 0.2, 0.3, 0.000001)
expect_near(sin(pi()), 0.0, 0.000001, "sin of pi")
```

**See also:** [`expect`](#expect), [`expect_eq`](#expect_eq)

### `safe_div`

```petal no-check
safe_div(a, b)
```

Division that returns `nil` instead of aborting when the divisor is zero.
Otherwise it is exactly `/`: int / int truncates, floats divide as floats.
Bare `/` aborts on a zero divisor by design; use `safe_div` where the divisor
comes from input or can legitimately be zero, and default with `??`.

**Example**

```petal
safe_div(7, 2)          # 3
safe_div(7.0, 2)        # 3.5
safe_div(1, 0)          # nil
safe_div(1.0, 0.0)      # nil
safe_div(3, 0) ?? 0     # 0
```

### `interp`

```petal no-check

```

The piecewise-linear function through a table of `[x, y]` knots (ascending
`x`), read at `x`: a schedule by year, a response curve, a falloff. Before

### `hash_int`

```petal no-check
hash_int(a: num, b?: num, c?: num, d?: num) -> int
```

A stateless hash of one to four numbers: an int from 0 to 2^53 − 1. The
result depends only on the arguments: it is the same in every run, on every
machine, in every module, and `--seed` does not touch it. An int and the
float of the same value hash alike (`2` and `2.0`).

Use it for generated content that must be the same every time — placement,
per-entity jitter, a stable pick — where `random()` would need a generator
carried in state: `hash_int(seed, i) % n` is pick `i` of `n`, and the result
is a seed for the next call (`hash_int(hash_int(seed, x), y)`). It is a
constant function, so a table built from it can be
[`const(…)`](language-guide.md#const--a-value-that-must-be-constant).

The algorithm is fixed and will not change. With `mix` one round of SplitMix64
(`x += 0x9e3779b97f4a7c15; x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9;
x = (x ^ (x >> 27)) * 0x94d049bb133111eb; x ^ (x >> 31)`, all in wrapping
64-bit arithmetic): start with `h = 0x243f6a8885a308d3`; for each argument, in
order, `h = mix(h ^ bits)`, where `bits` is the argument as an IEEE-754
double (`-0.0` taken as `0.0`); the result is `h >> 11`.

**Example**

```petal
hash_int(3, 7)                       # 8394216175903167
hash_int(3, 7) % 6                   # 3
["a", "b", "c"][hash_int(42, 5) % 3] # a
```

**See also:** [`hash01`](#hash01), [`hash_str`](#hash_str), [`random_int`](#random_int)

### `hash_str`

```petal no-check

```

An int from 0 to 2^53 − 1 from a string — an id, a name — and an optional
number. The same on every machine.

The algorithm, with `mix` as for `hash_int`: start with
`h = 0x452821e638d01377`; if there is a salt, `h = mix(h ^ bits(salt))`;
then `h = mix(h ^ n)` for the text's length `n` in UTF-8 bytes; then
`h = mix(h ^ w)` for each 8-byte little-endian word `w` of the text, the
last one zero-padded; the result is `h >> 11`.

**Example**

### `lerp`

```petal no-check
lerp(a, b, t: num)
```

Linear interpolation. `t=0` returns `a`, `t=1` returns `b`. `a` and `b` may
also be two `vec2`s or two `vec3`s, two colors, two equal-length lists of
numbers, or two records, interpolated component-wise. Colors blend like
`color_lerp`: per channel, alpha included, rounded to int channels.

Two **records** blend field by field, which is how a whole look, pose or
style is faded from one to another in one call. The result has `a`'s fields
(and its class). A field blends with the field of the same name in `b` when
both are numbers, vectors of one kind, colors, records, or equal-length lists
whose elements blend; anything else (a string, a bool, two different kinds)
is taken whole from `a` while `t < 0.5` and from `b` after. A field `b` does
not have keeps `a`'s value.

**Parameters**

- `a`: The start: what `t = 0` gives.
- `b`: The end: what `t = 1` gives.
- `t` (`num`): How far from `a` to `b`.

**Examples**

```petal
let noir   = {sepia: 0.0, grain: 0.8, tint: :202830, id: "noir"}
let golden = {sepia: 1.0, grain: 0.2, tint: :ffd08a, id: "golden"}
lerp(noir, golden, 0.25)   # { sepia: 0.25, grain: 0.65, tint: { r: 88, g: 82, b: 71 }, id: "noir" }
```

```petal
import vec2
lerp(0.0, 100.0, 0.3)   # 30.0
lerp(10.0, 20.0, 0.5)   # 15.0
lerp(vec3(0.0, 0.0, 0.0), vec3(10.0, 20.0, 30.0), 0.5)   # vec3(5.0, 10.0, 15.0)
lerp(:6a5a48, :ffd08a, 0.5)            # { r: 181, g: 149, b: 105 }
lerp([0.0, 10.0], [1.0, 20.0], 0.5)    # [0.5, 15.0]
```

## `vec2`

*Needs `import vec2`.*

2D and 3D vectors.

Needs `import vec2` (which declares `vec3` and the shared helpers too). The
import puts them in scope bare (`vec2(…)`), qualified (`vec2.vec2(…)`) and
as methods (`x.normalize()`).

Petal has built-in `vec2` and `vec3` types, backed by two and three f64s.
Both work with the usual arithmetic operators and share the helpers below
(`normalize`, `dot`, `limit`, plus `mag`, `distance` and `lerp` from the
core math builtins), which answer in the kind of vector they were given.
`rotate` is 2D-only and `cross` 3D-only.

Operators, for either kind:

- `a + b`, `a - b`, `a * b`, `a / b` between two vectors of the same kind work
  component-wise. Mixing a `vec2` with a `vec3` is an error.
- `v + s`, `v - s`, `v * s`, `v / s` with a number `s` apply `s` to every
  component; `s + v`, `s - v`, `s * v` work too.
- `-v` negates every component.
- `==` / `!=` compare components.
- `.x`, `.y` (and `.z` on a `vec3`) read a component as a float.

Both are small immutable heap objects. One visible difference: a zero `vec2`
is falsy in an `if`, while every `vec3` is truthy, like a record — compare
against `vec3(0, 0, 0)` explicitly. Both survive `json_stringify` /
`json_parse` (as `{"type": "vec3", "x": ..., "y": ..., "z": ...}`) and a
state save/restore.

**See also:** [`mag`](#mag), [`distance`](#distance), [`lerp`](#lerp)

### `format`

```petal no-check
format(template: string, ...args) -> string
```

printf-style templating. Each `%` placeholder takes the next argument:

| Placeholder | Meaning |
|---|---|
| `%s` | the value, as `str` renders it |
| `%d` | the value as a whole number (truncated toward zero) |
| `%f` | the value as a float; `%.2f` fixes two decimals |
| `%x` | the value in lowercase hex |
| `%%` | a literal `%` |

A `,` straight after the `%` groups thousands (`%,d`, `%,.2f`). A number
sets a minimum field width, padded on the left, or on the right when it is
written negative (`%8.2f`, `%-10s`). The placeholders start with `%` and not
`{` because `{` in a string literal opens an interpolation hole. `format` is
variadic and takes no named arguments.

**Example**

```petal
print(format("%s has %,d points (%.1f%%)", "Ana", 12345, 99.5))   # Ana has 12,345 points (99.5%)
print(format("%-6s|%6.2f|%x", "ab", 3.14159, 255))                # ab    |  3.14|ff
format("%s scored %d", "Ada", 97.8)       # Ada scored 97
format("%,.2f", 1234567.891)              # 1,234,567.89
format("[%5d] [%-5s]", 42, "ab")          # "[   42] [ab   ]"
```

### String offsets

Every string position counts **characters** (Unicode code points): `len(s)`,
`s.length`, `slice(s, a, b)`, `s[i]` and `index_of(s, needle)` all use the same
unit, so an offset one of them returns can be handed to another. In `"Óscar"`
the first character takes two bytes of storage, and `len("Óscar")` is still 5.

```petal
let s = "Óscar"
print(len(s))            # 5
print(s[0])              # Ó
print(s[-1])             # r
print(slice(s, 0, 2))    # Ós
print(index_of(s, "c"))  # 2
```

`s[i]` is the one-character string at index `i`. Like a list index it counts
from the end when negative and is an error when out of range; use
`char_at` where an out-of-range read should give `""`.

These are constant-time on a string that is all ASCII, however long. A string
containing a non-ASCII character is walked to find the position; reading it in
order (`s[i]`, then `s[i + 1]`) resumes from the last position, so a pass over
the whole string is still linear. To visit every character, `for c in chars(s)`
is the simplest form.

A code point is not always what a reader sees as one character: `"é"` written
as `e` plus a combining accent is two, and so is a flag emoji.

`chars`, `char_len`, `char_at` and `char_slice` date from when `len` and `slice`
counted bytes. `char_len` and `char_slice` now do exactly what `len` and `slice`
do on a string, and remain for existing scripts. `byte_len` and `byte_slice`
work in bytes of the UTF-8 encoding.

### Higher-order functions

`map`, `filter`, `reduce`, `forEach`, `sort_by`, `any`, `all` and `find`
call back into script code. A builtin may itself be the function:
`map(words, upper)`, `map(rows, len)`, `sort_by(names, lower)`,
`reduce(xs, 0, max)`.

A callback of any of these may not declare `state`: it runs once per element
and has no place in the program to keep a slot at. Reaching a `state` or
`state var` declaration from one is an error, and `petal lint` reports it
when it can prove it. A loop or `reduce`'s accumulator is the fix
([State is not allowed in callbacks](features/inline-state.md#state-is-not-allowed-in-callbacks)).

### Typed numeric arrays

An `f64_array` is a flat array of floats. It is faster than a list for numeric
inner loops (particle sims, grids, field evaluations) because its elements are
stored unboxed. Like lists, it is an immutable value: `set_at` and `swap`
return a new array, so keep the result.

Reading an element is plain indexing, and `a[i] = v` writes:

```petal
let a = f64_array(2)
a[0] = 2.5
a[0]             # 2.5
```

### `append`

```petal no-check
append(list, value)
```

Returns a **new** list with `value` added to the end. Lists are immutable
values, so `append` never changes its input — keep the result.

**Appending in a loop is linear.** When the binding being rebound is the
list's only holder, `append` adds to the list where it is instead of copying
it, so building a list of `n` elements this way costs `n` appends, not
`n²/2` element copies. That covers a `let` rebound with `=`
(`xs = append(xs, v)`), a `var` or a `state var` written
with `set` (`set xs = append(xs, v)`, `set xs = append(get xs, v)`), inside a
function or at the top level, and with reads of the list between the
appends. 10,000, 20,000 and 40,000 appends take 3.6, 4.0 and 4.9 ms as a
whole `petal run`, start-up included. There is no need to collect pieces
some other way and join them at the end.

Giving the list to something else is still free of surprises: `let snap =
xs` keeps what it read, and the next `append` pays for one copy before
carrying on in place. Three shapes still copy the whole list on **every**
append, and are quadratic (35, 127 and 565 ms for the same three sizes):

```petal ignore
set r.items = append(r.items, v)     # a list held in a record field
set grid[k] = append(grid[k], v)     # a list held in another list
set xs = add(xs, v)                  # through a function: fn add(xs, v) return append(xs, v) end
```

For those, build the list in a `var` of its own and store it once the loop
is done, or have the helper write the `var` itself (`fn add(v) set xs =
append(get xs, v) end`, called as a statement). A call inside the appended
value copies too, `set xs = append(xs, f(x))`, unless it is one of `float`,
`int`, `min`, `max`, `clamp`, `abs`, `floor`, `len` or `type`; bind
`let v = f(x)` first. The rules are in the language guide under
[`var`](language-guide.md#var-and-set).

**Example**

```petal
let items = [1, 2]
let more = append(items, 3)   # more is [1, 2, 3]; items is still [1, 2]
items = append(items, 3)      # grow an accumulator by rebinding
```

### `Map`

```petal no-check
Map() -> map
Map(pairs: list) -> map
```

A new **map**: a lookup table whose keys can be any value. Keys are compared
by content with the rule `==` uses (`m[[1, 2]]` finds the entry stored under
another `[1, 2]`; `2` and `2.0` are one key). `Map()` is empty; `Map(pairs)`
takes a list of `[key, value]` pairs, in order, and a repeated key keeps its
first place and its last value. Read with `m[k]` (an absent key is `nil`),
write with `m[k] = v` on a `let` or `set m[k] = v` on a `var`. `len`, `keys`,
`values`, `entries`, `contains` (by key), `remove` and `for k in m` take a
map; iteration is in insertion order. A function, a pending value or NaN
cannot be a key. See [Maps](language-guide.md#maps).

The name is capitalized like a class constructor's (`Rect`) because `map` is
the higher-order builtin.

**Parameters**

- `pairs` (`list`): A list of `[key, value]` pairs.

**Example**

```petal
let m = Map([["a", 1], [[0, 0], "origin"]])
m[3] = "three"
print(m[[0, 0]])   # origin
print(m["zz"])     # nil
print(len(m))      # 3
```

### `freeze`

```petal no-check
freeze(value)
```

Makes `value` and everything it holds frozen, and returns `value`. The
collector no longer looks inside a frozen value and never frees one. Lists,
records, strings, `f64_array`s, vectors and enum variants freeze, to any
depth. Freezing a number, a bool or `nil`, or a value that is already
frozen, does nothing.

The garbage collector visits every value the program still holds each time
it runs. For most programs that is cheap. For a program that keeps a very
large table for its whole life (a generated world, a rule table, a level
loaded from disk) it is a pause on every collection that grows with the
table: about 2.5 ms for 100,000 records, before any garbage is freed.
`freeze` takes such a value out of the collector's work. A frozen value is
still an ordinary value: it reads, compares, prints and passes around
exactly as before, and an update of it yields a new, unfrozen value as an
update of any value does.

The limits are part of the contract:

- **Freezing is one-way.** There is no unfreeze, and a frozen value is never
  freed, even after the program drops its last reference to it. The memory
  comes back when the program's heap goes away (the program is restarted or
  its context is dropped).
- **Freeze data that lives as long as the program**, once: in a `state`
  initializer, as in the example, or behind a check that it has not been built yet.
  `freeze` on a value rebuilt every frame leaks every one of them, so a
  top-level `let table = freeze(build())` in a script that runs once per
  frame is a leak. `state` initializers run once.
- **A top-level table that depends on no dynamic data is the exception to
  that**, where the host keeps static values between runs (it does by
  default; see [performance.md](dev/performance.md#static-values)): `let
  table = [...]` followed by `freeze(table)` freezes the one table the stack
  keeps, once, and `frozen(table)` is then true from the top of every later
  run. `let table = freeze(build())` is still rebuilt and frozen on every
  run, because a call of `freeze` is never static. With static values off
  both forms leak a table per run.
- **A value holding a function or a `var` cell cannot be frozen.** The call
  is an error (`freeze: the value holds a function, which cannot be frozen`)
  and nothing is frozen.
- **A hot reload keeps frozen values**, like the rest of the heap. A table
  that is rebuilt after a reload and frozen again leaves the old one
  allocated.
- **Freezing removes the value from a collection's work, not the rest of the
  heap.** A collection afterwards costs what the unfrozen data and the garbage
  cost. Freeze a table as soon as it is built: until then it is ordinary data
  and every collection during the build visits it.

A forked execution (and a snapshot restored from one) carries the frozen
values it was taken with.

**Example**

```petal
fn build_table(n)
  for i in range(0, n) do
    {id: i, name: "row " ++ str(i), tags: [i, i + 1]}

state table = freeze(build_table(1000))
print(frozen(table), len(table))      # true 1000

let longer = append(table, {id: 1000, name: "extra", tags: []})
print(frozen(longer), len(table))     # false 1000
```

**See also:** [`frozen`](#frozen)

*The prelude: Petal-source helpers in scope in every program; no import.*

### `min_by`

```petal no-check

```

The **element** whose `key(x)` is smallest, the first of equals; `nil` for
the empty list. `key` is called once per element and must return a number.

For the index instead, take `argmin` of the keys: `argmin(map(xs, key))`.

which calls nothing, and let `argmin` choose — it runs as fast as the
hand-written "best so far" loop:

```petal ignore
let nearest = stops[argmin(for s in stops do distance(s.at, here) end)]
```

**Example**

```petal

```

### `Rect`

```petal no-check
Rect(x, y, w, h)
```

A rectangle with fields `x`, `y`, `w`, `h`. An instance is an ordinary
record with a class tag, so anything that accepts an `{x, y, w, h}` record —
including every `petal-ui` draw call — accepts a `Rect`. (`petal-ui`'s
`rect(x, y, w, h)` is the same constructor.)

Each field holds exactly the number it was given, `int` or `float`:
`Rect(10.5, 20.9, 100.4, 40.6).x` is `10.5`. A non-numeric argument is an
error naming the field.

The methods are each exactly their equivalent expression, so an int rect
gives int answers (`/` on two ints truncates) and a float rect gives float
ones. `inset` and `offset` return a `Rect`, so calls chain.

| Method | Result | Equivalent |
|--------|--------|------------|
| `r.center_x()` | number | `r.x + r.w / 2` |
| `r.center_y()` | number | `r.y + r.h / 2` |
| `r.right()` | number | `r.x + r.w` (half-open, like the hit tests) |
| `r.bottom()` | number | `r.y + r.h` |
| `r.inset(n)` | `Rect` | pulled in by `n` on all four sides; a negative `n` grows it, and `w`/`h` clamp at 0 |
| `r.offset(dx, dy)` | `Rect` | moved by a delta, same size |

Add your own methods with `fn Rect.<name>(r: Rect, ...)`; a user declaration
wins over a built-in method of the same name.

**Examples**

```petal
let r = Rect(10, 20, 100, 40)
r.x            # 10
type(r)        # "Rect"
keys(r)        # ["x", "y", "w", "h"]
```

```petal
let card = Rect(0, 0, 100, 40)
card.center_x()             # 50
card.right()                # 100
card.inset(5)               # Rect(5, 5, 90, 30)
card.inset(5).center_x()    # 50
card.offset(10, 10).right() # 110

let sub = Rect(0.0, 0.0, 101.0, 40.0)
sub.center_x()              # 50.5, not 50
```

## `core/dm`

*In scope in every program; no import.*

Direct-manipulation hints: `tunable` and `rigid`, and the `const`
annotation.

Direct manipulation moves a number in the source when a shape is dragged or a
goal is set for an output: the tools re-run the program with literals nudged,
measure how the output moves, and change the literals that get it where it
should be, through function calls if need be
([dev/direct-manipulation-v2-plan.md](dev/direct-manipulation-v2-plan.md)).
Usually several literals could serve. `tunable` and `rigid` tell the tools
which ones to prefer and which never to touch. Both return their first
argument unchanged and do nothing else at run time; the tools read them from
the program. They are global (no import), and the names are reserved:
declaring a function, binding, parameter or loop variable called `tunable` or
`rigid` is a compile error.

**Settings.** A top-level `let` whose whole initializer is a `tunable(…)`
call is a *setting*: a binding hosts list, set live and override from
outside, of any data type. Hosts read `let SPEED = tunable(4.0, 0, 10)` as
the setting `4.0` with the range 0..10, and the path `SPEED` names the
`4.0`. This replaces `config let X = v`, which still works and means the
same but is deprecated: the compile check warns, and `petal
migrate-old-code` rewrites each one
([plan](tasks/lifecycle-annotation-functions-refactor.md)).

```petal
pub let SPEED = tunable(4.0, 0, 10)                                 # a number with a range
pub let START = tunable("title", options: ["title", "select", "play"])
pub let GOD = tunable(false)
pub let POST = tunable({exposure: 1.2, bloom: 0.32})               # every number is a knob
print(SPEED, START, GOD, POST.bloom)                               # 4.0 title false 0.32
```

A `var` is never a setting (`tunable-on-var`), and neither is a `let` with
the hint inside an operator, `let X = tunable(4) * 2`
(`tunable-not-whole-initializer`): there the hint only marks the `4`.

**See also:** [`tunable`](#tunable), [`rigid`](#rigid), [`const`](#const)

Source: [`core/packages/core/src/dm.ptl`](../core/packages/core/src/dm.ptl)

[`tunable`](#tunable) · [`rigid`](#rigid) · [`const`](#const)

### `tunable`

```petal no-check
tunable(value, min?: num, max?: num, step?: num, options?: list)
```

Marks a literal as a preferred target for direct manipulation, optionally
with a range and a step, and returns `value` unchanged. The literal `value`
is, or the literal a name in its place is bound to, becomes a preferred target for direct manipulation, kept within
`[min, max]` and to multiples of `step` when those are given. It can go at
the definition, at a use, or on a line of its own naming a binding.

Rules:

- `value` is a literal, a name bound to one, or data: a record, a list or a
  constructor call such as `rgb(255, 0, 80)`. A drag only moves numbers, so
  on data every number literal in it is marked (without bounds), and a
  string, bool or `nil` marks nothing but is still a valid setting.
- On a computed value (`tunable(a + b)`) nothing is marked, and `petal lint`
  reports `dm-hint-not-literal`. Wrap the literal itself: `tunable(a) + b`.
  For a setting it reports `config-not-data` instead, since hosts see no
  value.
- `min`, `max` and `step` describe a number, and are passed by position
  (in that order) or by name in any order: `tunable(4.0, min: 0, max: 10)`,
  `tunable(4.0, max: 10)`. On anything else they are ignored, with a
  `dm-hint-bounds` warning.
- On a declaration, `@tunable(…) let X = v` means `let X = tunable(v, …)`:
  `@tunable(0, 10) let speed = 4.0`, `@tunable(min: 0, max: 10)`. See
  [Writing an annotation with `@`](language-guide.md#writing-an-annotation-with-).
  `@rigid let X = v` and `@const let X = e` likewise.
- `options:` lists the values a setting can take, for a host to offer as a
  dropdown. `petal lint` reports `tunable-value-not-in-options` when `value`
  is not one of them; nothing else enforces it, and its numbers are never
  moved by a drag.
- The range is advice. Direct manipulation keeps a drag inside it; nothing
  else enforces it, and `set_config_value` / `pb_vm_set_tunable` do not clamp
  to it.
- The bounds must be number literals, and `min` must not be above `max`
  (`dm-hint-bounds`). A computed bound is evaluated and ignored.
- A bound is never edited itself: changing the range to reach a goal would
  defeat it.
- On a `state` initializer the hint cannot work, because a running program
  keeps its state across a reload (`dm-hint-state-init`). Put the start value
  in a setting, `let START = tunable(…)`, and initialise the state from it.

**Parameters**

- `value`: The literal (or name, or data) to mark; returned unchanged.
- `min` (`num`): The lowest a drag may take a number to.
- `max` (`num`): The highest a drag may take a number to.
- `step` (`num`): Keep a dragged number to multiples of this.
- `options` (`list`): The values a setting can take, for a host's dropdown.

**Returns** `value`, unchanged.

**Example**

```petal
let radius = tunable(40, 10, 80)               # at the definition
let gap = 12
tunable(gap, min: 0, max: 40, step: 2)          # a declaration on its own line
let dx = tunable(-5) + gap                      # at a use: only the -5 is marked
print(radius, dx)                               # 40 7
```

**See also:** [`rigid`](#rigid), [`const`](#const)

```petal no-check
tunable(value, options: list)
```

The form a setting with choices uses: `tunable("title", options: [...])`.

**Example**

```petal

```

*Source: [`core/packages/core/src/dm.ptl:104`](../core/packages/core/src/dm.ptl#L104)*

### `rigid`

```petal no-check
rigid(value)
```

Pins a literal so direct manipulation never moves it, and returns `value`
unchanged. The literal `value` resolves to is never moved by direct
manipulation, and nothing upstream of the call receives feedback through it:
while the tools measure, the call keeps answering what it answered in the
unmodified run. Use it for a number that has a perfectly good derivative but
is not a layout knob, such as an animation rate.

On a computed value (`rigid(a + b)`) it marks no literal and is still a
barrier: `a` and `b` can still move the output along any other path.

A host that registers a native named `rigid` (a physics engine's rigid-body
constructor) turns the hint off for that name, and the tools say so.

Natives can say the same about their own result: an effect row marked
`no_feedback` ([dev/native-effects.md](dev/native-effects.md)) keeps literals
that reach an output only through that native from being moved. `random`,
`random_int`, `choose`, `noise`, `hash_int`, `hash01` and `hash_str` are.

**Returns** `value`, unchanged.

**Example**

```petal
let t = 2.0
let angle = t * rigid(1.1)          # the rate stays; dragging moves the radius
let radius = tunable(11.0, 4, 30)
print(cos(angle) * radius > -12)    # true
```

**See also:** [`tunable`](#tunable)

*Source: [`core/packages/core/src/dm.ptl:140`](../core/packages/core/src/dm.ptl#L140)*

### `const`

```petal no-check

```

Requires a top-level binding to be static data, and returns `value`
unchanged. Not a direct-manipulation hint but an annotation of the same
kind (an [annotation](language-guide.md#annotations)): it changes only what

Anywhere else (inside a part of an initializer, a function body, a `var` or
a `state`) it is an error, and so is `const(tunable(…))`, which would hide
the setting. It replaces the `const NAME = e` declaration, which still works
and means the same but is deprecated (the compile check warns, and `petal
migrate-old-code` rewrites it;
[plan](tasks/lifecycle-annotation-functions-refactor.md)).

**Returns** `value`, unchanged.

**Example**

```petal

```

### `speculate`

```petal no-check

```

Calls `f(args...)` against the live program, then puts back every `state`

**Returns** `{value, emits, places}`.

```petal
  x * 2
print(speculate(view, 21).value)   # 42

```

## `autodiff`

*Needs `import autodiff`.*

Derivatives and solving by finite differences: deriv, jacobian, solve_step
and solve.

Needs `import autodiff`, which puts these in scope bare (`deriv(…)`),
qualified (`autodiff.deriv(…)`) and as methods.

Each function calls `f` with its inputs nudged (every call inside
[`speculate`](features/speculate.md), so nothing `f` writes or draws is left
behind) and measures how the output moved. `f` returns a number or a list of
numbers. Because every probe runs inside `speculate`, `f` may read and write
`state`, emit draw commands or call effectful natives; when the caller is
itself speculating (inside a `ui/drag` candidate rendering, or a `speculate`
call), the probes run directly, since the outer call already puts everything
back. The rules for each measurement's `quality`, the options and worked
examples are in [features/differentiation.md](features/differentiation.md).

### `deriv`

```petal no-check

```

The derivative of `f` at `x` by central differences, with
`h = 1e-4 * max(abs(x), 1)`. `quality` says whether `value` can be trusted

was measured with.

**Parameters**

**Options**

| Key | Meaning |
|---|---|
| `h` | The step to measure with, in place of the default. |
| `mode` | `"central"` (the default) or `"forward"` differences. |

**Returns** `{value, quality, step}`, plus `error` when `quality` is `"errored"`.

**Parameters**

- `xs`: The inputs to measure at.

**Options**

| Key | Meaning |
|---|---|
| `h` | The step to measure with, in place of the default. |
| `mode` | `"central"` (the default) or `"forward"` differences. |

**Returns** `{rows, quality, step}`.

**Example**

```petal
import autodiff
let j = jacobian(fn(p) [p[0] + p[1], p[0] * p[1]] end, [2.0, 3.0])
print(j.quality)   # ["smooth", "smooth"]
```

### `solve_step`

```petal no-check
solve_step(f, xs, target, opts = {})
```

One damped Gauss-Newton step from `xs` toward `f(xs) == target`, with the
Jacobian measured as `jacobian` does. A step that does not bring the output
closer is halved, up to four times; when none does, `xs` comes back
unchanged with `improved: false`.

The result: `xs`, the new inputs; `residual`, the distance from `f(xs)` to
`target` there; `improved`, whether the step got closer; `stuck`, the
indices of inputs that do not move the output (quality `"zero"` or
`"errored"`); and `quality`, the Jacobian's, one per input.

**Parameters**

- `f`: A list of numbers in, a number or a list of numbers out.
- `xs`: The inputs to start from.
- `target`: The output wanted: a number or a list of numbers.

**Options**

| Key | Meaning |
|---|---|
| `bounds` | `[[lo, hi], …]`, one per input; either end may be nil. |
| `max_step` | The most an input may move: a number for all, or one per input. |
| `damping` | The step's scale (default `1.0`). |
| `h` | As for `deriv`. |
| `mode` | As for `deriv`. |

**Returns** `{xs, residual, improved, stuck, quality}`.

**Example**

```petal
import autodiff
let r = solve_step(fn(p) [p[0] + p[1], p[0] - p[1]] end, [0.0, 0.0], [3.0, 1.0])
print(r.xs)   # [2.0, 1.0]
```

**See also:** [`solve`](#solve), [`jacobian`](#jacobian), [`gn_step`](#gn_step)

*Source: [`core/packages/autodiff/autodiff.ptl:165`](../core/packages/autodiff/autodiff.ptl#L165)*

### `solve`

```petal no-check
solve(f, xs, target, opts = {})
```

`solve_step` repeated until `residual` is at most `tol`, `max_iter` steps
are spent, or a step stops improving. The result is `solve_step`'s record
from the last step, with `improved` true when any step improved, plus
`iterations`.

**Parameters**

- `f`: A list of numbers in, a number or a list of numbers out.
- `xs`: The inputs to start from.
- `target`: The output wanted: a number or a list of numbers.

**Options**

| Key | Meaning |
|---|---|
| `tol` | The residual that counts as solved (default `1e-6`). |
| `max_iter` | The most steps to take (default 20). |
| `bounds` | As for `solve_step`. |
| `max_step` | As for `solve_step`. |
| `damping` | As for `solve_step`. |
| `h` | As for `deriv`. |
| `mode` | As for `deriv`. |

**Returns** `{xs, residual, improved, stuck, quality, iterations}`.

**Example**

```petal
import autodiff
let s = solve(fn(a) 200.0 + 80.0 * cos(a[0]) end, [0.6], 240.0)
print(round(s.xs[0], 4))   # 1.0472
```

**See also:** [`solve_step`](#solve_step)

### `drag_triangulate`

```petal no-check
drag_triangulate(points: list) -> list
```

A Delaunay triangulation of `points` (`[[x, y], …]`), as `[[i, j, k], …]`
point indices, each triangle counter-clockwise. A point equal to an earlier
one is left out; fewer than three distinct points, or all on one line, give
`[]`.

**Example**

```petal
drag_triangulate([[0, 0], [100, 0], [0, 100]])   # [[0, 1, 2]]
```

**See also:** [`drag_weights`](#drag_weights)

*Source: [`core/packages/core/src/drag_math.ptl:29`](../core/packages/core/src/drag_math.ptl#L29)*

### `drag_weights`

```petal no-check
drag_weights(points: list, tris: list, x: num, y: num) -> list
```

One weight per point for `(x, y)`, summing to 1: the barycentric weights in
the triangle of `tris` that holds it. A point outside every triangle is
first moved to the nearest point of their edges (clamped to the hull). With
no triangles — two points, or points on a line — it is the projection onto
the nearest segment between neighbours along the line.

**Parameters**

- `points` (`list`): `[[x, y], …]`.
- `tris` (`list`): A triangulation of `points`, as `drag_triangulate` gives.
- `x` (`num`): The point's x.
- `y` (`num`): The point's y.

**Example**

```petal
let pts = [[0, 0], [100, 0], [0, 100]]
let tris = drag_triangulate(pts)
print(tris)                                  # [[0, 1, 2]]
print(drag_weights(pts, tris, 25, 25))       # [0.5, 0.25, 0.25]
print(drag_weights(pts, tris, 50, -40))      # [0.5, 0.5, 0.0]
print(drag_weights([[0, 0], [100, 0]], [], 25, 30))  # [0.75, 0.25]
```

### `gn_step`

```petal no-check
gn_step(values: list, rows: list, targets: list, jac: list, bounds, scale: num) -> list
```

One Gauss-Newton step of the direct-manipulation solver (`core/src/dm`) for
the levers `values` (`k` numbers). Returns the next values, each clamped
into its bounds. When the levers outnumber the goals, the step moves each in
proportion to its size. `ui/drag`'s `vary` and the `autodiff` package's
`solve_step` take their steps through it.

**Parameters**

- `values` (`list`): The levers: `k` numbers.
- `rows` (`list`): The goals' current values (`m` numbers; for a dragged point, its `[x, y]`).
- `targets` (`list`): Where the goals should be (`m` numbers; for a dragged point, the pointer's `[x, y]`).
- `jac` (`list`): `m` rows of `k` sensitivities.
- `bounds`: nil, or one `[lo, hi]` (or nil; either end may be nil) per lever.
- `scale` (`num`): Shortens the step: 1 for a full one.

**Returns** The next values, `k` numbers.

**Example**

```petal
let jac = [[2.0]]   # y = 2·v, now 2 at v = 1; the pointer wants y = 10
print(gn_step([1.0], [2.0], [10.0], jac, nil, 1))       # [5.0]
print(gn_step([1.0], [2.0], [10.0], jac, [[0, 3]], 1))  # [3.0]
```

**See also:** [`autodiff.solve_step`](#solve_step), [`fd_column`](#fd_column)

*Source: [`core/packages/core/src/drag_math.ptl:79`](../core/packages/core/src/drag_math.ptl#L79)*

### `fd_column`

```petal no-check
fd_column(x: num, base, samples: list, opts)
```

One finite-difference column, classified by the direct-manipulation rules
(`core/src/dm/jacobian.rs`): what `autodiff`'s `deriv` and `jacobian` are
built on. Returns a float, the next point to measure (call again with it
added to `samples`), or the finished `{value, quality, step}` (see
`autodiff.deriv`).

**Parameters**

- `x` (`num`): Where the column is measured.
- `base`: The function at `x`: a number or a list of numbers.
- `samples` (`list`): Its values measured so far, as `[[x_i, y_i], …]`.
- `opts`: nil or `{h, mode}`.

**Options**

| Key | Meaning |
|---|---|
| `h` | The step to measure with. |
| `mode` | `"central"` or `"forward"`. |

**Example**

```petal
let f = fn(x) x * x end
let samples = []
let r = fd_column(3.0, f(3.0), samples, nil)
while type(r) == "float" do
  samples = append(samples, [r, f(r)])
  r = fd_column(3.0, f(3.0), samples, nil)
print(r.quality)   # smooth
```
