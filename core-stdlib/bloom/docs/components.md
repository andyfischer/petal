# `bloom` reference

*Generated from the `@doc` and `@module_doc` in the sources (`npm run reference`); edit those, not this page.*

A UI component library written entirely in Petal. Buttons, menus, controls,
text and inspector fields, tabs, splitters, tables, overlays, an animation
core and a vector icon set, on top of `ui`'s host layer.

Import this module and you have the whole library:

```petal
import bloom                      # bloom.button(r, "Save")
import bloom: button, dropdown    # button(r, "Save")
```

Import one module instead when you want only a slice of it
(`import bloom/motion: spring` in a game's HUD). Every export of every
`bloom/…` module is re-exported here under its own name.

Conventions used throughout:

- **Rects** are `rect(x, y, w, h)` (the built-in `Rect`) or any `{x, y, w, h}`
  record. **Colors** are `{r, g, b}` records; hex literals like `:3c8cff` work.
- **A component returns its value**, on the frame it changes: `button` returns
  true when clicked, `switch(r, on)` returns the new bool. There are no
  callbacks and no event objects.
- **The last argument is always an optional `opts` record.** Any key it omits
  comes from the theme, so `{}` (or the shorter arity) is the themed component.
- **Animation is internal.** Every component holds its own animators in
  call-path-keyed `state`. Two callsites never share them; a component inside a
  `for` loop gets one animator per iteration.
- **Every export is type-annotated**, so `petal lint` catches a wrong argument
  at the callsite rather than at the draw call. A rect parameter is `record`,
  not `Rect`, because of the first convention: both spellings are accepted,
  and `Rect` would reject the plain-record one.

bloom sits on top of `petal-ui`'s host layer (the input and draw natives and
the `ui` prelude's primitives) and adds a component layer with its own theme,
its own interaction model (press-and-release clicks, one open menu, input
capture for overlays) and animation in every component by default. It is pure
Petal: no Rust, no assets. It works in any host that provides the `ui`
interface.

bloom owns the widgets; `ui` keeps the primitives and the interaction logic
under them. Layout (`cut_left`, `row`, `col`, `pad`, `split_h`), list and
scroll state (`list_update`, `scroll_update`), the editing logic behind a
field (`text_field_update`, `text_area_update`), the keyboard focus
(`has_focus`, `focus_request`, `shortcut`), drag and drop, the load state,
gradients, layers and the draw primitives all still come from there, and
bloom paints through them. Mixing the two in one script is expected:

```petal
import bloom

let all = rect(0, 0, screen_width(), screen_height())
let bar = cut_top(all, 34)                  # ui layout
if bloom.button(bar.cut, "Run") then        # bloom component
  run()
```

bloom's focus *is* `ui`'s: `bloom.focused(id)` is `has_focus(id)`, and a
field built on `text_field_update` and a bloom control share one keyboard
owner. bloom adds the draw-order Tab ring on top.

`ui`'s own drawn widgets (`ui.button`, `ui.text_field`, `ui.context_menu`,
…) are deprecated: each call warns `[ui-widget-moved]` with its bloom
replacement, and they go once the deprecation period ends; the table of
replacements is in `docs/tasks/ui-refactor.md`. They click on press where
bloom clicks on release, so two components of different families stacked on
the same pixel would both see the same gesture.

The runnable tour is `examples/ui/bloom-gallery`.

## `bloom/theme`

The theme tokens and the painting primitives every bloom component shares:
text styles and placement, surfaces, outlines, washes, the focus ring and the
late paint layer.

bloom does not own a palette. It *derives* one: `theme()` starts from
whatever the host published through the `ui` prelude (Garden binds its
editor palette, the SDL and canvas hosts bind theirs, and a bare host falls
back to the built-in dark theme), then layers bloom's own tokens — motion
speed, the tone ramp, the focus ring — over it, then any override the app
set with `theme_set`. So a bloom panel looks native in its host on the first
frame with no setup, and an app that wants a look of its own overrides one
key rather than a palette.

Every label bloom draws is placed by `text_layout`, which asks the host where
a run's ink actually lands rather than assuming it is `size` px tall starting
at `y`. That is why a bloom label is centered on the line it claims to be on,
and why a component's own text needs no arithmetic from the caller. Reach
past bloom for it (`import text_layout`) when a panel draws text of its own.

### `theme`

```petal
theme() -> record
```

The live token record: the host palette (whatever `ui_theme()` resolves to:
Garden's editor colors, an SDL app's, the built-in dark default), then
bloom's own tokens over it, then the app's `theme_set` overrides over those.

The host supplies the colors: `bg`, `panel`, `surface`, `overlay`, `text`,
`muted`, `dim`, `accent`, `success`, `warn`, `danger`, `outline`, `border`,
`hover`, `selection`, the `space_*` / `radius_*` / `font_*` scales and
`elevation_1/2/3`. bloom adds numbers only, so they stay right in a light
theme and a dark one:

| Token | Default | Role |
|---|---|---|
| `speed` | 1.0 | multiplies every duration; `theme_set({speed: 0})` freezes the UI for a pixel diff |
| `hover_rate` / `press_rate` | 18 / 34 | how fast the interaction fades run |
| `open_dur` | 0.16 | menu / popover entrance |
| `press_scale` | 0.97 | how far a face squashes when pressed |
| `radius` / `radius_sm` / `radius_lg` / `radius_pill` | 7 / 4 / 12 / 999 | corner scale |
| `pad_x` / `pad_y` / `gap` / `row_h` | 12 / 7 / 8 / 30 | rhythm |
| `hover_pct` / `press_pct` / `ring_pct` / `border_pct` | 8 / 14 / 55 / 14 | ink strengths, in percent |

**Returns** A fresh record of every token; changing it changes nothing.

**Example**

```petal
let t = bloom.theme()
draw_rect_rounded(r, t.radius, t.panel)
```

### `overlays`

```petal
overlays()
```

Paint the late layer: everything deferred this frame. Call it as the last
line of the frame; calling it twice, or when nothing is pending, does
nothing.

A menu's popup belongs above everything, but the call that opens it sits
where its button is, usually early in the frame. So menus and tooltips hand
their painting to a closure (`defer_paint`), and `overlays()` runs them. An
app that never calls it still gets its overlays: they are painted at the
first bloom overlay call of the next frame, which is where an immediate-mode
library would have drawn them anyway. So this is an improvement to opt into,
never a way to lose a menu. `defer_paint` puts your own painting on the same
layer.

Dialogs, popovers and toasts paint immediately, because the app draws *into*
them right after the call; put those calls late in the frame yourself.

**Example**

```petal
bloom.overlays()   # the last line of the frame
```

**See also:** [`defer_paint`](#defer_paint)

### `text_in`

```petal
text_in(s: string, r: record, style: record, align: string)
text_in(s: string, r: record, style: record)
```

Draw one line of text inside `r`, aligned, and vertically centered, which is
what every control wants.

"Vertically centered" means the *cap height* is centered, not the line box.
The difference is the whole reason this goes through text_layout rather than
the `r.y + (r.h - size) / 2` it used to compute: a run's ink does not start
at `y` and is not `size` px tall, so that arithmetic put every label in
bloom a pixel high at 14 px and three high at 32 — consistently enough that
it read as a style rather than as a bug.

**Parameters**

- `s` (`string`): The text.
- `r` (`record`): The box.
- `style` (`record`): A text style record (`ts`).
- `align` (`string`): `"left"` (the default), `"center"` or `"right"`.

**Returns** The run's width, for a caller flowing something after it.

**Example**

```petal
let w = bloom.text_in("Name", row, bloom.ts(t, 13, t.muted))
```

**See also:** [`text_block_in`](#text_block_in), [`text_cut`](#text_cut)

## `bloom/icon`

bloom's icon set: 22 glyphs drawn as vectors.

No font, no atlas, no asset pipeline: every glyph is a handful of strokes in
a unit box, scaled into whatever rect it is given. A host that can draw a
line can draw the whole icon set, and an icon inherits its color, weight and
size from the control around it instead of from a font file that has to ship
beside the script.

## `bloom/motion`

The animation core bloom's components are built from: eased and spring
values, entrances, impulses, clock-driven waves, easing curves and rect
interpolation. Use it directly for anything the components do not cover.

Every value here is *per callsite*: the `state` inside these functions is
keyed by the call path, so a component that calls `ease_flag(hover, 18)`
gets its own animator per instance with nothing to plumb through the app.
That is the whole trick behind bloom's components animating by default —
there are no animation state records, no ids, and no registration.

A call in a loop gets one animator per iteration, so a list of buttons
animates independently. The corollary: animators follow the *position*, so
reordering a list makes item 3's motion state stay with slot 3.

Almost everything here integrates `dt()`, the host's frame delta, which the
headless harness pins — so a bloom UI settles identically in a trace and on
screen. The two exceptions are `wave` and `pulse`, which read the wall clock
`time()` so that every callsite sharing a period stays in phase; a headless
run holds that clock still, and they hold their value with it.

**See also:** [`ease_to`](#ease_to), [`spring`](#spring), [`enter`](#enter)

## `bloom/interact`

bloom's interaction layer: pointer probes, dragging, the keyboard focus and
its Tab ring, hotkeys, and the input capture that lets an overlay drawn
*last* still swallow the click.

A probe is the unit every bloom component is built on. It answers the
pointer questions for one rect (hovering? held? clicked?) and, in the same
record, the *animated* versions of those answers (`hot`, `active`), because
a component that has to ask twice — once for the logic, once for the fade —
is where hand-rolled UIs start to drift.

Click means press-and-release inside, not press. Pressing a button and
sliding off it cancels, which is what every real toolkit does and what
makes a drag out of a menu item work.

Tab and Shift+Tab walk the ring the previous frame built (the only complete
ring that exists when the key arrives), so focus moves on the frame after the
keypress. With nothing in the ring focused, Tab focuses its first control;
`tab_enters_ring(false)` turns that off.

**See also:** [`probe`](#probe), [`capture`](#capture), [`focusable`](#focusable)

### `capture`

```petal

```

## `bloom/fields`

The text fields (`text_field`, `text_area`) and a property inspector's fields
(`commit_field`, `number_field`, `color_field`, `swatches`).

The editing is `ui`'s: `ui.text_field_update` and `ui.text_area_update`
hold the caret, the selection, the clipboard and undo, and own the
keyboard through the runtime focus. bloom paints them and puts each one in
its Tab ring. So a bloom field selects, copies, pastes and undoes like a
desktop field, and shares one keyboard owner with any `ui` code beside it.

Every field takes its focus id as `opts.id`. A field without one falls
back to its placeholder, then to "field" — enough for the one search box
of a panel, and wrong for two fields: give each its own id.

The inspector fields (`commit_field`, `number_field`, `color_field`) apply
only when the edit is done: the result holds the new value on the frame it
is committed (Return, or the field losing the keyboard) and the old one,
or nil, before. Escape abandons the edit and gives the focus up. Each keeps
its edit in widget `state`, keyed per callsite — so in a loop, key it by
the row (`for p in props key p.name do … end`).

`ui` keeps `color_to_hex`, `color_from_hex` and `same_color` for color text
of your own.

## `bloom/menu`

Menus: the popup `menu`, and the `dropdown`, `select`, `menu_bar` and
`context_menu` built on it.

One menu is open at a time, program-wide, and the library holds that fact,
not the app: `menu(id, anchor, items)` returns the index of the item chosen
on the frame it is chosen and -1 otherwise. There is no menu state record to
thread, and a second menu opening closes the first because they are asking
the same cell.

While a menu is open it *captures* input (see bloom/interact), so the panel
underneath goes inert for exactly as long as the menu is up — no ordering
discipline, no `if !m.open` around every other control.

An item is a string, or a record: `{label, hint, icon, disabled, sep,
danger}`. `sep: true` draws a divider and cannot be chosen. Menus flip up and
pull left rather than draw off-screen, handle up/down/Return/Escape, close on
an outside click, and capture input while open: bloom's own probes, and,
through `ui_modal` on a high layer, every control built on `ui.interact`.

## `bloom/overlay`

The things that float above a panel: tooltips, toasts, dialogs, popovers,
banners and loading skeletons.

Overlays are the part of a UI where immediate mode usually goes wrong: the
dialog is drawn last but has to eat the input first, and the toast has to
outlive the frame that raised it. Both are handled here — dialogs claim
input through `bloom/interact`’s `capture`, and toasts live in a module-level
queue with their own clocks, so `toast("Saved")` from anywhere is a complete
interaction.

Tooltips paint on the late layer (`overlays`). Dialogs and popovers paint
immediately, because the app draws *into* them right after the call: put
those calls late in the frame.

**See also:** [`dialog`](#dialog), [`toast`](#toast), [`bloom/theme.overlays`](#overlays)

### `dialog`

```petal

```

**Example**

  bloom.text_in("This cannot be undone.", d.content, bloom.ts(t, 13, t.muted))
